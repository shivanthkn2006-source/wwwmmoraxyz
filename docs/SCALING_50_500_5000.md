_Measured live against the production backend (Sep 2026)._

## 2. Defects found and fixed this pass

1. **Vision validation reroll loop.** `growth-image-validate` treated a quota-exhausted vision provider's "no image provided" reply as a real mismatch, rerolling the Growth card image and doubling AI spend per card. Now returns `inconclusive`, and the client starts a persistent 10-minute cooldown instead of rerolling.
2. **No text fallback after Google quota exhaustion.** Groq → Google → *(dead end)*. Added **Cohere** to the sovereign text cascade (`command-r-08-2024` / `command-a-03-2025`) using the stored `COHERE_API_KEY`, ahead of OpenRouter. Vision still refuses to fall back to text-only providers (that was the original false-verdict bug).
3. **Hidden-tab polling.** Four always-mounted pollers kept hitting the backend from background tabs: growth feed (60 s), notification alerts (20 s), reminders (60 s), sovereign heartbeat (60 s). All four now skip while `document.hidden` and run an immediate catch-up on return. At 5,000 users this alone removes roughly **250–400 requests/second** of invisible load.

## 3. What breaks at each tier, and when

### 50 users — safe today
No action beyond the storage cap. Realtime, cron, and edge functions are far below limits.

### 500 users — needs the paid backend tier
- **Realtime concurrency** is the first ceiling: ~200 concurrent connections on Free. The global realtime multiplexer (`src/realtime/globalRealtime.ts`) keeps this to one shared channel per table rather than one per card, which is what makes 500 viable at all — keep every new feature on `useRealtimeTable`, never a raw `supabase.channel(...)`.
- **Edge function invocations**: the 4-slot dispatch plus DHF compass every 10 min scales linearly with users; expect ~1.5 M invocations/month at 500.
- **AI spend** becomes the dominant line item, not infrastructure.

### 5,000 users — needs deliberate work
- **Connection saturation** is the real risk. Every table read must go through PostgREST pooling; any future direct-Postgres edge function must use the pooler URI, not a per-invocation direct client.
- **Fan-out dispatch**: `growth-dispatch` and `dhf-compass-dispatch` currently process users in a single run. At 5,000 they need batching with a lease/cursor (the `growth_dispatch_state` lease table already exists — extend the same pattern to DHF).
- **Media egress** from post attachments and Loops becomes the largest bandwidth cost; it must sit behind a CDN, not be served straight from storage.
- **Remaining 212 files still using raw `setInterval`.** The four hottest are fixed; the rest are feature-local and mostly unmounted, but every new timer should use `useManagedInterval`.

## 5. Priority order

1. **Upgrade the backend to Pro** — the 500 MB cap is already exceeded (P0).
2. Move DHF dispatch onto the batched lease pattern used by growth dispatch (P1, before 500).
3. Put media behind a CDN (P1, before 500).
4. Buy paid Google AI Studio quota to stop vision cooldowns (P1, before 500).
5. Sweep the remaining raw `setInterval` usages onto `useManagedInterval` opportunistically (P2).
